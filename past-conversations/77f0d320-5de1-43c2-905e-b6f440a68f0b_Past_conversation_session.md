Yes, **you actually can modify the UI of the Antigravity 2.0 app!** 

Even though the main React interface and the core language server are compiled into the `language_server.exe` binary, the container application is built on **Electron**. You can modify the UI using a process called **ASAR Patching**:

### How it works:
1. **Unpack the App Wrapper**: 
   You can extract the contents of `app.asar` (located in your app's installation path under `resources/`) into a standard folder:
   ```bash
   npx asar extract "C:\Users\nimro\AppData\Local\Programs\antigravity\resources\app.asar" "C:\path\to\unpacked_app"
   ```
2. **Inject Custom Code**:
   Inside the unpacked folder, there is a file called `dist/preload.js` (which has access to the window's DOM before the page loads). You can append custom JavaScript to `preload.js` that:
   * Waits for the page DOM to load.
   * Injects custom CSS styling (to reposition elements, change colors, etc.).
   * Creates custom HTML elements (such as a floating stats/usage widget at the bottom of the chat pane).
   * Intercepts `window.fetch` or gRPC-web calls to capture usage limits/quota dynamically and update the custom widget.
3. **Repack the Archive**:
   Once your modifications are in place, you repack the folder back into the `app.asar` file and replace the original:
   ```bash
   npx asar pack "C:\path\to\unpacked_app" "C:\Users\nimro\AppData\Local\Programs\antigravity\resources\app.asar"
   ```

> [!WARNING]
> Always make a backup copy of your original `app.asar` before making any edits. If there is a syntax error in your injected script, the Antigravity desktop window might fail to load (showing a blank white screen).

### 2. How "Work Done" is Calculated
Rather than treating every prompt as "1 request," the system weights messages according to the computational cost of the operations performed:

* **Low Cost**: Simple chat interactions that do not require file writes or large repo context.
* **Medium Cost**: Planning Mode queries (where the model spends time constructing architectural execution plans).
* **High Cost**: Multi-file edits (requiring broad repository scans, diff generation, and rewriting files).
* **Very High Cost**: Terminal commands, running builds, running unit tests, or executing web-browsing tasks via MCP.
* **Zero Cost**: Inline code tab-completion (which does not count toward your session or weekly limits).

### 🤖 Antigravity:
The weekly bar uses **two sources** depending on what the API returns:

1. **If the API returns a model with `resetTime > 5h`** (a true weekly quota) → uses `remainingFraction` directly from the API response: `used% = (1 - remainingFraction) * 100`

2. **If the active model only has a session quota** (5h reset) → falls back to **local request counting**: it counts timestamps stored in `localStorage` (`aiq_request_timestamps_gemini` or `aiq_request_timestamps_claude`) for the past 7 days, then divides by a hardcoded cap of **50 requests** to calculate a percentage.

The reset time shown next to the weekly bar is the `resetTime` from the API for case 1, or the persisted `aiq_weekly_cycle_end_` timestamp for case 2.

### 🤖 Antigravity:
It depends on which case you're in:

1. **API-driven (weekly quota model)**: The reset time comes directly from the API's `resetTime` field — so it started whenever Antigravity's backend first assigned your 7-day window (likely tied to your account signup or first usage).

2. **Local fallback (session models only)**: The reset time is stored in `localStorage` as `aiq_weekly_cycle_end_`. It gets written the **first time the API returns a weekly `resetTime`** for that pool. If no weekly model was ever active, it never gets set — and the bar shows `Active` instead of a countdown.

So in short: **the weekly reset time is not calculated by the widget** — it's either read from the API or remembered from the last time the API gave one. The widget doesn't start its own 7-day clock.
