When connecting a GitHub MCP server to an AI assistant, it is best practice to follow the **Principle of Least Privilege**. You should only grant the minimum level of access required for the tasks you want the assistant to perform.

Here is a breakdown of how you should scope the access:

### 1. When to use Read-Only vs. Read/Write
* **Read-Only Access (Recommended for Audits/Analysis)**:
  * *Use case*: If you want the assistant to read your codebase, analyze files, help you debug, or write documentation.
  * *Why*: This is the safest option. It eliminates the risk of the assistant accidentally modifying code, deleting branches, or making unauthorized changes.
* **Read & Write Access (Required for active development)**:
  * *Use case*: If you want the assistant to write code directly to GitHub, create new branches, push commits, or open Pull Requests for you.
  * *Why*: The assistant needs write permissions to push code and create/manage repository resources.

---

### 2. Best Practices for Setting Up Access
To keep your GitHub account secure, follow these guidelines:

1. **Use Fine-Grained Personal Access Tokens (PATs)**:
   Instead of using "Classic" tokens (which grant access to all repositories on your account), use GitHub's **Fine-grained PATs**. This allows you to:
   * Limit access to **only specific repositories** (e.g., just the project you are working on, rather than your entire account history).
   * Define specific permission scopes (e.g., allow `Contents: Read/Write` and `Pull Requests: Read/Write`, but keep all other settings disabled).
2. **Never grant Administrative Scopes**:
   Do not check permissions for repository administration, organization settings, billing, or security settings. The assistant does not need these to write or read code.
3. **Monitor Token Expiry**:
   Set a short expiration date (e.g., 30 or 90 days) on the token so it automatically deactivates if no longer needed.
